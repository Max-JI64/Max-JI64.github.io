## 프로젝트 한눈에 보기

정책자금을 찾은 뒤에도 소상공인에게는 한 가지 판단이 더 남는다. 지원금이나 신규 정책자금이 당장의 현금 부족을 해결하는지, 부족 시점만 늦추고 부채와 상환 부담을 키우는지 확인해야 한다. 버팀AI는 이 판단을 돕기 위해 만든 서울 소상공인 대상 정책금융 영향 시뮬레이터다.

사용자가 상권과 업종, 최근 매출, 보유 현금, 비용, 기존 대출을 입력하면 아무 정책도 이용하지 않은 경우를 먼저 계산한다. 이후 비차입 지원과 신규 정책자금(융자)을 같은 일정에 적용해 <strong>첫 현금 부족 시점</strong>, <strong>13주차 현금</strong>, <strong>6개월 뒤 남은 부채</strong>, <strong>월 최대 상환액</strong>, <strong>만기까지 총이자</strong>를 비교한다. 정책 목록보다 이용 전후의 재무 결과를 보여주는 데 초점을 맞췄다.

대표 가상 사례에서는 신규 정책자금이 13주 안의 현금 부족을 해소하는 대신, 6개월 뒤 남은 부채가 무대응보다 <strong>17,559,958원</strong> 늘어났다. 반면 비차입 지원은 신규 부채가 없지만 선지출과 자부담 때문에 13주차 현금이 무대응보다 <strong>750,000원</strong> 적었다. 이 결과는 실제 사업장 예측이 아니라 동일한 금융 계산 구조를 설명하기 위한 고정 사례다.

## 해결하려던 문제

정책금융 서비스는 보통 이용 가능한 지원사업이나 대출상품을 찾는 데 집중한다. 그러나 현금이 부족하고 기존 대출이 있는 사업장에는 정책의 이름보다 지급 시점, 선지출해야 할 자부담, 거치기간과 상환 시작일이 더 중요할 수 있다. 같은 3,000만 원이라도 언제 들어오고 언제부터 갚는지에 따라 다음 13주의 현금 부족 시점과 6개월 뒤 부채가 달라지기 때문이다.

중소벤처기업부가 공개한 소상공인 폐업 현황에서는 폐업 결심 당시 부채 보유 비율이 <strong>68.5%</strong>, 평균 부채가 <strong>8,531만 원</strong>으로 나타났다. 폐업 절차의 가장 큰 애로사항도 <strong>대출금 상환 45.5%</strong>였다. 이 수치는 정책 탐색만큼 기존 부채와 신규 자금의 상환 부담을 함께 확인하는 일이 중요하다는 문제의식을 뒷받침했다.

### 정책 목록에서 금융 결과로 질문을 바꾸기

| 일반적인 정책 탐색 | 버팀AI가 답하려는 질문 |
| --- | --- |
| 내가 신청할 수 있는 정책은 무엇인가 | 그 정책을 이용하면 현금 부족 시점이 실제로 달라지는가 |
| 지원금액과 금리는 얼마인가 | 지급 및 상환 일정을 반영하면 13주차 현금이 얼마 남는가 |
| 대출을 받을 수 있는가 | 6개월 뒤 남은 부채와 월 상환액이 얼마나 늘어나는가 |
| 어떤 정책이 유리한가 | 무대응과 비교했을 때 현금 개선과 부채 증가를 함께 감수할 수 있는가 |

버팀AI는 공식기관의 승인 판단이나 최종 신청을 대신하지 않는다. 사용자가 정책을 선택하기 전에 금융 결과와 확인할 조건을 정리하고, 마지막 판단은 공식 공고와 신청기관으로 연결한다.

## 금융 비교 설계

정책의 효과를 비교하려면 정책을 이용하지 않았을 때의 결과가 먼저 필요하다. 버팀AI는 현재 입력과 상권환경 범위로 무대응 기준선을 계산한 뒤, 각 정책의 지급과 상환 사건을 같은 일정에 추가한다.

### 계산에 사용하는 입력

사용자는 최근 3개월에서 12개월의 매출, 보유 현금, 주요 비용과 기존 대출을 입력한다. 현금흐름은 금액뿐 아니라 시점에 따라 달라지므로 매출 유입일, 비용 지출 구간과 대출 상환 일정도 함께 반영한다.

| 입력 묶음 | 주요 항목 | 계산에서의 역할 |
| --- | --- | --- |
| 사업장 | 서울 상권, 업종 | 같은 상권과 업종의 매출환경 참고 범위 연결 |
| 매출 | 최근 월매출, 유입 시기 | 기준 매출과 주차별 현금 유입 일정 구성 |
| 보유 현금 | 계산 시작일의 가용 현금 | 모든 대안의 공통 시작 잔액 |
| 비용 | 임대료, 인건비, 기타 고정비, 지출 시기 | 주차별 현금 유출 일정 구성 |
| 기존 대출 | 남은 원금, 금리, 상환방식, 잔여기간 | 6개월 부채와 월별 상환 부담 계산 |

사용자가 고른 해결 목적은 먼저 볼 지표와 정책 검토 순서만 바꾼다. 자격조건, 정책 금액, 정책 효과와 금융 계산 결과에는 영향을 주지 않는다.

### 무대응 기준선을 먼저 계산한 이유

```text
무대응 = 현재 현금 + 예정 매출 - 운영비 - 기존 대출 상환

비차입 지원 = 무대응 + 지원금 지급 - 선지출 및 자부담

신규 정책자금 = 무대응 + 대출 실행액 - 신규 원리금 상환
```

모든 대안에서 사업장 입력, 상권환경 범위와 계산 시작일을 동일하게 유지한다. 정책마다 다른 기준선을 사용해 효과가 커 보이는 문제를 막기 위한 구조다.

### 정책 조건을 금융 사건으로 바꾸기

| 정책 조건 | 금융 일정에 반영하는 방식 |
| --- | --- |
| 지원 및 융자 금액 | 지급일의 현금 유입으로 반영 |
| 지급 시점 | 공고에서 확인한 날짜 또는 사용자가 확인한 가정일에 반영 |
| 자부담 및 선지출 | 실제 지출 시점의 현금 유출로 반영 |
| 금리 | 신규 정책자금의 이자 계산에 사용 |
| 거치기간 | 원금 상환이 시작되기 전 기간으로 반영 |
| 상환방식 및 기간 | 월별 원금과 이자, 6개월 뒤 남은 부채 계산에 사용 |

공고에 금액이나 시점이 없으면 서비스가 임의로 채우지 않는다. 사용자가 직접 확인한 가정을 넣은 경우에만 조건부 계산을 제공하고, 그래프와 결과 카드에 확정 결과가 아님을 표시한다.

### 비교 지표

| 지표 | 계산 목적 | 사용자가 확인할 질문 |
| --- | --- | --- |
| 첫 현금 부족 시점 | 현금잔액이 처음 0원 아래로 내려가는 주차 확인 | 정책이 위기 시점을 실제로 늦추는가 |
| 13주차 현금 | 단기 운영기간 말의 현금 여력 확인 | 세 달 뒤에도 운영자금이 남는가 |
| 6개월 뒤 남은 부채 | 기존 및 신규 대출의 남은 원금 확인 | 단기 현금 개선의 대가로 부채가 얼마나 늘어나는가 |
| 월 최대 상환액 | 가장 부담이 큰 달의 원리금 확인 | 매출이 줄어도 감당할 수 있는 상환액인가 |
| 만기까지 총이자 | 전체 금융비용 확인 | 낮은 월 상환액 뒤에 큰 총비용이 남는가 |

## 진단부터 신청 준비까지

서비스는 회원가입 없이 <strong>진단 → 비교 → 준비</strong>의 세 단계로 이어진다.

### 진단: 사업장과 재무 일정을 입력한다

먼저 서울 상권과 업종, 현재 가장 해결하고 싶은 문제를 고른다. 이후 최근 매출, 매출 유입 시기, 보유 현금, 월 임대료와 인건비, 기타 고정비, 기존 대출을 입력한다. 금액과 시점을 함께 받아 주차별 현금 일정에 반영한다.

### 비교: 무대응과 정책 대안을 같은 일정에서 본다

입력값과 서비스에 등록된 공식 공고를 바탕으로 비교할 정책 후보를 최대 3개 제시한다. 사용자는 정책이 필요한 이유, 공고 확인 항목과 입력값 기준의 제한 가능성을 확인한 뒤 비교 대상을 직접 선택한다.

### LightGBM Quantile로 세 가지 환경을 만든 이유

평균값 하나만 제시하면 매출이 나빠지는 경우와 회복되는 경우를 함께 검토하기 어렵다. 버팀AI는 Quantile 회귀로 P10, P50, P90을 산출하고 화면에서는 하방, 기준, 회복으로 표현한다.

| 모델 출력 | 화면 표현 | 사용 방식 |
| --- | --- | --- |
| P10 | 하방 | 상대적으로 낮은 매출 변화 가정 |
| P50 | 기준 | 중앙 수준의 매출 변화 가정 |
| P90 | 회복 | 상대적으로 높은 매출 변화 가정 |

모델은 같은 상권과 업종의 다음 1분기와 다음 2분기 합산 매출 증감률을 산출한다. 13주 계산에는 다음 1분기 값을, 6개월 계산에는 다음 2분기 합산 값을 매출 유입 일정에 적용한다.

P10, P50, P90은 개별 점포 매출의 확률이나 보장된 예측구간이 아니다. 모델은 주차별 현금, 개인 사업장의 폐업 가능성이나 대출 승인 여부를 직접 예측하지 않는다. 주차별 현금과 부채는 모델 출력에 사용자 현금, 비용, 대출과 정책 일정을 더한 금융 계산 엔진이 산출한다.

### 현재 제시할 수 있는 검증 범위

현재 준비된 포트폴리오 근거에는 LightGBM Quantile의 독립 평가 성능 수치가 포함되어 있지 않다. 따라서 이 페이지에서는 모델이 산출한 범위를 정책 성과나 개인 점포의 예측 정확도로 확대하지 않는다. 후속 보강에서는 학습 및 평가 구간, Quantile 손실과 구간별 검증 결과를 실제 실행 기록으로 확인한 뒤 추가해야 한다.

## AI와 금융 결정의 경계

생성형 AI가 자연스럽게 설명하는 능력과 자격 및 금융 결과를 결정하는 권한을 분리했다. 자격 상태, 정책 금액, 현금흐름, 부채와 비교 순위는 공식 규칙과 금융 계산 엔진이 결정한다.

| 구성 요소 | 수행하는 일 | 수행하지 않는 일 |
| --- | --- | --- |
| LightGBM Quantile | 상권과 업종 집계의 매출환경 범위 산출 | 개별 점포의 매출, 폐업과 승인 예측 |
| 생성형 AI | 사용자가 동의한 가정 문장을 허용된 변경값으로 해석 | 자격조건, 정책 금액과 금융 결과 변경 |
| 공고 분석 | 등록된 공식 공고를 여섯 신청정보 항목으로 정리 | 공고에 없는 값 추정 |
| 정책 상담 | 선택 정책과 공식 근거 범위에서 질문 설명 | 최종 자격 및 승인 판단 또는 금융 중개 |
| 공식 규칙 엔진 | 공고 조건과 사용자 답변을 대조해 서비스 기준 상태 산출 | 공식기관 판단 대체 |
| 금융 계산 엔진 | 무대응과 정책 적용 후의 현금, 부채, 상환 부담 계산 | 정책 효과의 인과관계 확정 |

이 구조에서는 생성형 AI가 응답하지 않아도 핵심 진단과 정책 비교를 제공할 수 있다. AI 출력이 금융 결과에 영향을 주는 경우에도 허용 범위와 숫자 형식을 확인한 뒤 금융 계산 엔진이 다시 계산한다.

### 공식 공고의 근거 확인

공고에서 확인한 신청 기간, 금융 조건, 신청 경로, 필요 서류, 문의처와 게시일을 항목별로 제시한다. 공고에 없는 금리, 지원금액과 신청기간은 생성하지 않는다. 근거를 찾지 못한 항목은 `공식 공고에서 확인`하도록 표시하고 원문 링크로 연결한다. 현재 접수 여부, 잔여 예산과 최신 변경사항도 공식기관 확인 대상으로 남긴다.

### 개인정보와 외부 전송 범위

- 수집하지 않는 정보: 주민등록번호, 사업자등록번호, 계좌번호, 카드번호, 개인 신용점수
- 현재 탭에만 유지하는 정보: 월매출, 보유 현금, 비용, 기존 대출, 정책별 조건 답변
- 서버에서 일시 처리하는 정보: 사용자가 계산을 요청한 재무 입력과 정책 조건
- 서비스에 저장할 수 있는 정보: 서비스에 등록된 공개 공고의 검증된 분석 결과
- 외부 AI 전송 대상: 사용자가 동의한 가정 문장, 등록된 공개 공고, 금액과 식별정보를 제거한 정책 질문
- 외부 AI에 보내지 않는 정보: 재무 원장, 월매출, 현금, 비용, 대출과 금융 계산 결과

사용자의 상담 대화와 재무 입력은 서비스 데이터베이스나 공고 검색자료에 장기 저장하지 않는다. 외부 AI 전송이 필요한 기능은 별도 동의를 받고, 동의하지 않아도 재무 진단과 정책 비교를 이용할 수 있다.

### 실패 상황에서 값을 만들지 않기

| 실패 상황 | 처리 방식 |
| --- | --- |
| 공고에서 필수 조건을 찾지 못함 | 값을 추정하지 않고 공식 공고 확인으로 전환 |
| 사용자 자격 답변이 비어 있음 | 조건부 또는 추가 확인 필요 상태로 표시 |
| 생성형 AI 호출 실패 | 규칙과 금융 계산 결과는 유지하고 AI 기능만 중단 |
| AI가 공고 근거 밖의 숫자를 제시함 | 결과에 반영하지 않음 |
| 최신 접수 상태를 확인할 수 없음 | 공식기관에서 현재 상태를 다시 확인하도록 안내 |

## 구현 결과와 남은 검증

FastAPI와 JavaScript로 웹서비스를 구현하고 Google Cloud Run에 배포했다. 사용자는 대표 가상 사례로 비교 방식을 먼저 확인하거나 자신의 조건을 입력해 진단, 정책 비교와 신청 준비를 진행할 수 있다. 구현에서는 한 줄짜리 추천보다 현금 개선과 부채 증가를 같은 계산표에서 확인할 수 있게 하는 데 집중했다.

현재 서비스에서 다루지 않는 범위는 다음과 같다.

- 개별 사업장의 매출, 폐업 가능성과 정책 및 대출 승인 예측
- 현재 접수 상태, 잔여 예산, 최종 자격과 실제 지원금액의 확정
- 사용자 계정, 계좌와 POS 자동 연동, 알림과 재무정보 장기 저장
- 기관으로 개인정보나 신청서 전송
- 자동 신청, 대출 중개와 금융상품 계약
- 실제 사용성, 정책 신청 성과, 매출 개선과 폐업 감소의 검증

현재 공개 서비스는 기능 흐름과 계산 가능한 결과를 구현한 단계다. 후속 검증에서는 실제 소상공인이 비교 지표를 이해하는지, 정책 선택 전에 현금 개선과 부채 증가를 함께 고려하게 되는지를 먼저 확인해야 한다. 이후 분기의 독립 데이터로 상권환경 모델을 재검증하고, 기관 협력과 공고 갱신 체계가 마련되기 전까지는 공식 공고와 신청기관의 최신 판단을 우선한다.

## 판단과 시행착오
