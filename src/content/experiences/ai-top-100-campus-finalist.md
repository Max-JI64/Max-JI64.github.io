## 프로젝트 한눈에 보기

AI TOP 100 CAMPUS에서는 PDF, 표, 채팅 스크린샷, 이미지, 음성과 같이 형식이 다른 자료를 읽고 제한 시간 안에 답을 만들어야 했다. 문제마다 필요한 자료와 판단 방식이 달랐기 때문에, 하나의 긴 프롬프트에 원문과 질문을 모두 넣는 방식으로는 풀이 과정을 통제하기 어려웠다. 자료를 많이 읽을수록 컨텍스트가 커졌고, 추출과 판단 및 계산을 한 번에 맡기면 틀린 답이 어느 단계에서 생겼는지 찾기도 힘들었다.

나는 문제를 바로 푸는 프롬프트 대신 <strong>계획 수립 프롬프트</strong>와 <strong>문제 풀이 지시 프롬프트</strong>를 따로 만들었다. 첫 번째 프롬프트는 필요한 파일, 판단 기준, 도구와 시간 예산을 `plan.md`에 적는다. 두 번째 프롬프트는 그 계획을 문항별로 실행하고, 추출·판단·계산 결과를 `answer_qN.md`에 남긴다. 이 방식을 실제 대회 문제에 적용했고 <strong>본선에 진출</strong>했다.

## 한 번에 잘 답하게 만드는 대신 작업 순서를 고정했다

처음부터 정답을 요구하면 LLM은 자료 탐색, 문맥 해석, 수치 계산과 답안 작성을 한 응답 안에서 처리한다. 빠르게 보이지만 중간 결과가 남지 않는다. 계산이 틀려도 원문을 잘못 읽은 것인지, 조건을 잘못 적용한 것인지, 산술에서 실수한 것인지 구분하기 어렵다.

이를 막기 위해 전체 흐름을 다음 파일 계약으로 고정했다.

```text
README.md + question.md
→ BASE.md
→ plan.md
→ prompt.md
→ answer_qN.md
```

| 파일 | 역할 | 다음 단계에 넘기는 내용 |
| --- | --- | --- |
| `README.md`, `question.md` | 대회가 제공한 문제 설명과 문항 | 조건, 데이터 형식, 답안 형식 |
| `BASE.md` | 분석 계획 수립 프롬프트 | 문제를 풀지 않고 실행 계획만 작성 |
| `plan.md` | 문항별 작업 명세 | 필요한 데이터, 판단 기준, 실행 순서, 도구, 시간과 확인 항목 |
| `prompt.md` | 문제 풀이 지시 프롬프트 | 계획을 벗어나지 않도록 실행 규칙 적용 |
| `answer_qN.md` | 문항별 작업 기록 | 추출값, 판단 근거, 계산 결과와 최종 답안 |

두 프롬프트에는 서로 다른 책임이 있었다. <strong>계획 단계는 답을 미리 풀지 않고, 실행 단계는 정해진 계획을 임의로 바꾸지 않는다.</strong> 파일은 세션이 바뀌어도 같은 기준을 이어받는 상태 저장소로 사용했다.

## 프롬프트 1. 문제를 풀지 않는 분석 계획 수립 프롬프트

첫 번째 프롬프트의 역할은 `plan.md` 작성으로 제한했다. 원문에도 다음 문장을 중복해서 넣을 정도로 계획과 실행의 경계를 강하게 고정했다.

```text
이 채팅의 역할은 계획 수립입니다. 문제를 직접 풀지 않습니다.
이 계획 채팅에서는 plan.md 작성까지만 수행합니다.
Python 실행, 데이터 분석, 답안 도출은 절대 하지 않습니다.
```

### 먼저 읽을 것과 읽지 않을 것을 정했다

계획 채팅은 `README.md → question.md → 예시 파일 → 폴더 구조` 순서로 확인한다. 실제 문제 데이터는 모두 열지 않고 파일명, 확장자와 값의 구조까지만 살핀다. 소스코드도 문제 설명만으로 규칙을 알 수 있으면 읽지 않는다. 계획에 필요하지 않은 파일을 더 읽는 행동 자체를 시간 낭비로 정의했다.

반면 문제 설명에서 예시 파일을 직접 참조하면 계획을 쓰기 전에 반드시 확인하게 했다. 예시가 이미지이면 직접 읽고, 텍스트 중심 PDF이면 Python으로 변환한다. 레이아웃과 도표가 중요한 PDF나 자동 판독이 불안정한 음성은 사용자가 내용을 확인한 뒤 다음 단계로 넘어가도록 했다.

### 모든 문항을 같은 형식의 실행 명세로 바꿨다

`plan.md`의 문항별 항목은 자유로운 설명문이 아니라 아래 필드를 가진 작업 지시서다.

| 계획 항목 | 기록하는 내용 |
| --- | --- |
| 문항 요약과 답안 형식 | 무엇을 구해야 하는지, JSON·파일명·복수 선택 등 어떤 형태로 제출하는지 |
| 필요한 데이터 | 읽어야 할 파일과 이미 확보된 전처리 결과 |
| 사전 준비 | 사용자가 실행할 명령어, 외부 도구에 붙여넣을 프롬프트, 육안 확인 항목 |
| 판단 기준 | 모호한 표현의 기준과 객관식 선택지를 대입하는 규칙 |
| 풀이 전략 | 추출, 해석, 판단, 계산과 검증의 순서 |
| 결과물 | `answer_qN.md`, Python 파일, 영상 등 남겨야 할 파일 |
| 실행 조건 | 추천 모델, 예상 시간, 다른 문항과의 의존성 |

객관식 문제에서는 선택지에 맞춰 추출값을 수정하지 못하게 했다. 원문에서 얻은 값을 먼저 저장하고 각 선택지를 대입한다. 어떤 선택지와도 맞지 않으면 데이터를 억지로 맞추지 않고 사용자에게 보고하도록 했다. 앞 문항의 결과가 다음 문항의 입력으로 쓰일 수 있기 때문에, 이 규칙은 정답 선택보다 원본값 보존을 우선한다.

### 데이터 형식마다 다른 전처리 규칙을 넣었다

| 입력 | 계획 프롬프트가 만드는 지시 |
| --- | --- |
| 텍스트 중심 PDF | `extract_pdf_text.py` 실행 명령과 변환 결과 확인 |
| 도표가 포함된 PDF | 텍스트 추출 후 해당 페이지를 사용자가 다시 확인 |
| 이미지 | 최대 5장씩 나눠 분석하고 배치마다 즉시 Markdown으로 저장 |
| 채팅 스크린샷 | 촬영자에 따라 달라지는 "나"를 구분하고, 배경 이미지의 말풍선은 제외하며, 겹치는 메시지를 제거 |
| 음성 | STT 결과를 Markdown으로 저장한 뒤 분석 |
| CSV·엑셀 | Python으로 구조화, 집계와 계산 수행 |
| URL 목록 | 샘플 페이지를 먼저 받아 실제 HTML 구조와 셀렉터를 확인한 뒤 크롤러 작성 |

이미지는 여러 장을 한꺼번에 넣지 않았다. 다섯 장을 처리할 때마다 파일별 제목을 붙여 결과를 저장하고 다음 묶음으로 넘어가게 했다. 채팅 스크린샷은 앞 이미지의 마지막 메시지와 다음 이미지의 첫 메시지를 대조해 중복 구간을 제거하도록 했다. 단순히 "이미지를 분석해"라고 요청하는 대신, 자주 생기는 오독을 프롬프트 규칙으로 미리 막았다.

### 계획이 끝없이 길어지는 것도 막았다

계획 자체가 문제 풀이보다 오래 걸리면 역할 분리가 의미가 없다. 그래서 다음 중단 기준을 프롬프트에 적었다.

- 문항 분석이 3분을 넘을 것 같으면 방향만 남기고 실행 채팅으로 넘긴다.
- 연산 추적 문제는 손으로 계산하지 않고 "Python으로 계산"까지만 정한다.
- 인코딩 문제는 숫자 관계, 빈도, 시퀀스, 구조적 인코딩 순서로만 가설을 확인한다.
- 코드 규칙이 문제 설명에 충분히 적혀 있으면 구현 파일을 추가로 읽지 않는다.

프롬프트의 목적은 가능한 모든 경우를 분석하는 것이 아니라, 실행 채팅이 바로 시작할 수 있는 최소한의 작업 지시서를 만드는 것이었다.

실행 채팅은 먼저 공통 규칙과 필수 참조 파일을 읽고, 지정된 문항의 판단 기준과 풀이 순서를 그대로 사용한다. 이후 추출, 해석, 판단, 계산과 검증을 나눠 수행하며 각 단계가 끝날 때마다 `answer_qN.md`를 갱신한다. 문항을 마치면 `plan.md`의 체크박스도 `[x]`로 바꾼다.

### LLM이 멋대로 일을 늘리지 못하게 한 실행 규칙

| 통제 대상 | 프롬프트에 넣은 규칙 | 의도 |
| --- | --- | --- |
| 수치 계산 | 단순 사칙연산도 Python 파일로 실행 | 계산식과 결과를 다시 실행할 수 있게 함 |
| 단계 혼합 | 추출, 해석, 판단, 계산, 교차 검증을 차례로 기록 | 잘못된 결론이 생긴 위치를 찾기 쉽게 함 |
| 원문 과다 입력 | 전체 원문 대신 구조화된 표와 100자에서 200자 문맥만 전달 | 자료 탐색보다 판단에 컨텍스트를 사용 |
| 대량 항목 | LLM 입력이 20건 이상이면 Python으로 먼저 팩트 표 생성 | 반복 추출을 자연어 추론에서 분리 |
| 세션 과부하 | 답안 파일이 50KB를 넘거나 분석이 10단계 이상이면 새 세션으로 전환 | 긴 대화에서 기준과 중간 결과가 흐려지는 문제 방지 |
| 과도한 탐색 | 4중 이상 반복문 금지, 100만 조합 이상이면 가지치기 적용 | 제한 시간 안에서 접근법을 다시 설계 |
| 실행 지연 | 문항당 5분, 코드 실행 30초를 상한으로 설정 | 느린 접근을 붙잡고 있는 시간 제한 |
| 중복 검산 | 선택지와 일치하면 경량 검산 1회 후 종료 | 같은 문제를 여러 방식으로 다시 푸는 행동 제한 |

수치 계산을 Python에 맡기면 코드 파일에 입력, 공식과 출력이 남는다. 결과가 이상할 때 같은 입력으로 다시 실행하거나 공식만 확인할 수 있다. LLM은 문항 해석과 코드 설계, 결과 해석을 담당하고 실제 산술은 코드 결과를 사용하게 했다.

### 추출과 판단 사이에도 경계를 뒀다

```text
기계적 추출 → 맥락적 해석 → 판단 → 계산 → 교차 검증
```

예를 들어 여러 기사에서 설립연도를 비교하는 문제라면, Python이 먼저 날짜, 직함과 앞뒤 문맥을 표로 만든다. LLM은 그 표에서 값이 다른 항목을 해석하지만 이 단계에서는 아직 정답을 정하지 않는다. 판단이 끝난 뒤 계산이 필요하면 다시 Python으로 넘긴다. 마지막에는 결론과 관련된 근거만 한 번 더 확인한다.

이 구조는 LLM이 자신의 이전 판단을 다시 읽고 계속 번복하는 일을 줄이기 위한 장치였다. 동시에 각 단계의 결과가 파일에 남기 때문에, 새 세션에서도 전체 원문을 다시 읽지 않고 이전 단계부터 이어갈 수 있었다.

## 사람, LLM과 Python의 책임을 나눴다

| 담당 | 맡긴 일 | 넘지 못하게 한 경계 |
| --- | --- | --- |
| LLM | 요구사항 해석, 계획 작성, 자연어 문맥 해석, 코드 작성과 결과 설명 | 숫자를 직접 계산하거나 불확실한 시각 정보를 확정하지 않음 |
| Python | 정규식 추출, 파싱, 불일치 탐지, 집계와 수치 계산 | 문맥의 의미나 최종 제출 판단을 대신하지 않음 |
| 사용자 | 시각 자료 원본 확인, 외부 도구 실행, 애매한 조건과 최종 답안 검토 | 자동 판독 결과를 근거 없이 승인하지 않음 |

사람을 마지막 승인 버튼으로만 두지는 않았다. 계획 단계에서 자동으로 읽기 어려운 자료를 발견하면 필요한 페이지나 장면을 구체적으로 요청하고 대기하게 했다. 사용자가 확인한 결과는 다시 파일에 기록되어 다음 세션의 입력이 됐다.

## 실제 적용 예시. 수능 경향 분석 문제

남아 있는 `plan.md` 예시는 수능 통계, 국어·사회탐구 문제지, 영어 듣기 대본과 영상 제작이 섞인 네 문항을 다룬다. 같은 문제 묶음 안에서도 필요한 도구가 달라 프롬프트의 역할 분리가 가장 잘 드러난다.

| 문항 | 문제 유형 | 계획에서 정한 처리 방식 |
| --- | --- | --- |
| 1 | 2022학년도부터 2026학년도까지 수능 통계 주장 검증 | 응시·접수·채점 자료를 Python으로 파싱한 뒤 선택지별 조건 계산 |
| 2 | 제2외국어 비율과 국어 난이도 지수 비교 | 계산식을 먼저 고정하고 Python으로 연도별 지수와 비율 산출 |
| 3 | 세 수능 문제의 출처 파일 식별 | 국어·사회탐구 PDF를 텍스트로 변환하고 키워드 검색 후 원본 파일명 대조 |
| 4 | 영어 듣기 상황을 바탕으로 60초 이내 영상 제작 | 대본 검색, 정답 선지 확인, 장면 구성과 영상 제작을 분리하고 최종 대사는 원문과 대조 |

### 문항 3에서는 검색 코드를 계획서 안에 먼저 만들었다

브레턴우즈 체제, 위약금, 리카도 비교생산비설이 등장하는 문제의 출처를 찾기 위해 국어와 사회탐구 PDF를 먼저 Markdown으로 변환하도록 했다. 그다음 Python이 `브레턴우즈`, `플라자`, `위약금`, `위약벌`, `리카도`, `비교 우위` 같은 키워드를 전체 변환 파일에서 찾고 후보 파일명을 출력한다. LLM이 여러 문제지를 처음부터 읽는 대신, 검색 결과의 앞뒤 문맥만 비교해 네 글자 파일 접두사를 정하도록 했다.

### 문항 4에서는 분석과 제작 시간을 분리했다

영어 듣기 대본에서 산, 사진, 셀카와 관련된 표현을 검색한 뒤 해당 문항의 정답 선지를 원본 문제지에서 확인하도록 했다. 이후 등장인물, 장소, 촬영 행동과 마지막 대사를 정리해 영상 프롬프트를 만드는 순서다. `plan.md`는 20분 안에 대본 분석과 영상 프롬프트 작성까지 배치하고, 실제 영상 생성 시간은 별도로 구분했다. 제한 시간 안에 끝낼 수 없는 제작 작업을 분석 시간에 억지로 포함하지 않았다.

### 20분을 문항별 실행 순서로 바꿨다

| 시간 | 계획한 작업 |
| --- | --- |
| 0분부터 3분 | 채점 자료 재추출과 국어·사회탐구·영어 PDF 변환을 동시에 시작 |
| 3분부터 8분 | 이미 확보한 응시·접수 자료로 문항 1의 계산 가능한 선택지부터 검증 |
| 8분부터 12분 | 키워드 검색 결과로 문항 3의 출처 파일 확인 |
| 12분부터 16분 | 추가 채점 자료로 문항 2와 문항 1의 나머지 선택지 계산 |
| 16분부터 20분 | 문항 4의 대본 분석과 영상 프롬프트 작성 |

문항 번호대로 진행하지 않고, 전처리 대기 시간과 문항 의존성을 기준으로 순서를 바꿨다. 계획서에는 어떤 작업을 동시에 시작할 수 있는지, 어떤 데이터가 와야 다음 단계로 넘어갈 수 있는지도 함께 적었다.

## 프롬프트에서 확인할 수 있는 설계 판단

### 프롬프트는 설명문이 아니라 실행 계약이었다

입력 파일, 출력 파일, 도구, 시간, 중단 조건과 사용자 확인 항목을 명시했다. 덕분에 새 채팅을 시작해도 `plan.md`와 이전 `answer_qN.md`를 읽으면 어느 단계부터 이어가야 하는지 알 수 있었다.

### 정확도라는 말보다 오류를 찾는 경로를 남겼다

현재 자료에는 전체 문항 정확도나 재현율을 입증하는 정량 평가가 없다. 그래서 이 페이지에서는 "정확도 100%"라고 쓰지 않는다. 대신 추출값, 판단 기준, 계산 코드와 최종 답안을 분리해 오류가 발생한 단계를 다시 확인할 수 있게 했다는 사실만 설명한다.

### Human-in-the-loop를 구체적인 행동으로 바꿨다

"사람이 검토한다"는 선언만으로는 실행되지 않는다. 프롬프트는 어떤 PDF 페이지를 열어야 하는지, 어떤 이미지가 자동 판독에 불리한지, 객관식 값이 맞지 않을 때 언제 멈춰야 하는지를 사용자 행동으로 적게 했다. 사람이 개입하는 위치와 이유가 계획서에 남도록 만든 것이다.

## 산출물과 결과

- 문항별 데이터, 판단 기준, 도구, 출력 파일과 예상 시간을 작성하는 <strong>분석 계획 수립 프롬프트</strong>
- 수능 경향 분석 네 문항에 프롬프트를 적용한 <strong>분석 계획 예시</strong>
- 계획을 단계별 실행과 파일 기록으로 전환하는 <strong>문제 풀이 지시 프롬프트</strong>
- AI TOP 100 CAMPUS <strong>본선 진출</strong>

현재 폴더에서 직접 확인할 수 있는 결과물은 완성된 AI 서비스가 아니라 프롬프트와 계획 문서다. RAG 데이터베이스, Planner와 Worker의 실제 병렬 운영 성능, 멀티모달 파이프라인의 전체 구현 결과는 남아 있는 자료만으로 확인할 수 없어 공개 성과로 쓰지 않았다.

## 이 경험에서 남은 기준

긴 프롬프트가 곧 좋은 프롬프트는 아니었다. 실제로 도움이 된 부분은 역할을 나누고, 입력을 줄이고, 결과를 파일로 남기고, 멈춰야 할 시점을 숫자로 정한 규칙이었다. 이후 AI를 활용할 때도 먼저 묻는 것은 같다. 어떤 판단은 코드로 확인할 수 있는가, 어떤 판단은 사람이 원본을 봐야 하는가, 다음 사람이 같은 결과를 다시 확인하려면 무엇을 남겨야 하는가.
